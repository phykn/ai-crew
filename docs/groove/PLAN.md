# AI Crew 핵심 기능 구현 계획

## Core

사용자는 비서하고만 대화하며, 비서는 직접 답하거나 팀의 전략·실행·검증을 조율해 같은 채팅으로 결과를 돌려준다.

## Requirements

- R1: 로컬 폴더를 프로젝트로 열고 세션을 만들 수 있다. 프로젝트와 세션 사이를 이동해도 맡겨 둔 업무는 계속 진행한다. 앱을 완전히 종료한 뒤 이전 세션을 로드하면 마지막 상태와 남은 일이 표시되고, 사용자가 이어가라고 할 때 실행을 재개한다.
- R2: 에이전트마다 작업 맥락을 유지하는 세션이 있다. 이전 업무를 다시 맡으면 자기 세션에서 이어간다. 같은 에이전트 세션은 한 번에 한 업무를 실행한다. 사용자와 비서의 발언은 대화 탭에, 동료의 위임과 진행은 로그 탭에 표시한다.
- R3: 비서는 간단한 요청에는 바로 답한다. 협업이 필요한 개발 업무는 `플랜 → 개발 → (리뷰 ∥ 코딩 스타일 확인 ∥ 테스트) → 비서 확인`로 진행한다. 개발 담당은 사용자가 연 프로젝트 폴더를 직접 수정한다. 최신 변경을 검증한 뒤 비서가 결과를 보고한다. 같은 결과에 대한 추가 수정은 기존 업무와 이력에서, 별개의 요청은 새 업무에서 처리한다.
- R4: 역할별 지침과 도구 권한을 UI에서 확인할 수 있다. 이전 세션의 설정을 로드해도 현재 권한을 실행에 적용한다. 새 접근과 회수된 권한의 재요청에는 프로젝트의 현재 승인 모드(수동·자동·항상)를 적용한다. 수동은 사용자, 자동은 비서가 판단하고 항상은 현재 역할 권한 안의 요청을 자동 승인한다. 담당자나 도구가 바뀌거나 승인 범위가 넓어지면 새 요청으로 처리한다. 신규 에이전트와 알바도 같은 규칙을 따른다.
- R5: 진행 중 추가 지시는 해당 업무에 반영한다. 일시적 실패는 같은 단계에서 최대 3회 재시도하고, 검증 실패는 수정·재검증을 최대 3회 반복한다. 해결되지 않으면 비서가 막힌 부분을 보고한다. 중단은 해당 업무와 후속 단계에 적용하고, 완료와 경합하면 먼저 저장된 상태를 따른다. 기존 변경을 보존한 채 마지막 확인 상태에서 이어갈 수 있다.
- R6: 대화창 상단에는 진행 중인 업무별 고정 카드를 둔다. 현재 권한 승인 카드는 입력창 위에 한 번 표시하고 답변을 해당 업무에 연결한다. 완료 보고에서 업무 로그를 바로 연다. 업무별 로그에 위임·검증·실패·재시도·인사 결정과 결과물 근거가 시간순으로 남는다.
- R7: 기존 팀에 필요한 능력이 없으면 인사팀이 정규 팀원 또는 알바를 생성·고용한다. 비서는 채택·투입과 해고를 판단한다. 알바는 목적을 달성하면 결과와 업무 기록을 남기고 퇴장한다.
- R8: 첫 버전부터 사용자가 에이전트별로 Codex 또는 연결한 로컬 LLM을 고를 수 있다. 같은 업무에서 두 실행 환경의 에이전트가 협업하고, 로컬 모델의 결과도 업무 로그와 비서 보고에 반영된다.
- R9: 이전 세션을 로드하면 팀·모델 선택과 작업 맥락을 이어간다. `/clear`는 팀·모델·워크플로우 선택을 이어받은 빈 세션을 만든다. 기존 업무는 원래 버전을 쓰고, 새 업무에는 선택한 워크플로우의 최신 버전과 현재 권한을 적용한다. 프로젝트 공통 규칙과 이전 세션 이력은 계속 사용할 수 있다.
- R10: 프로젝트별 워크플로우와 메모리를 관리한다. 사용자와 크루는 프로젝트 공통 메모리를 공유 위키로 읽고 갱신하며, 사용자는 문서가 쌓이는 과정을 변경 타임라인에서 확인한다. 지속 규칙은 다음 새 업무부터 적용하고, 사용자가 지정하면 현재 업무에 적용한다. 메모리 탭에서 연결된 규칙을 확인하고, 기억만 지울지 규칙도 해제할지 선택할 수 있다.
- R11: 범례에 에이전트만 나열하고, 역할 오른쪽의 별명을 누르면 그 자리에서 편집할 수 있다. 정규 팀원은 해고 후에도 설정과 함께 범례에 남고, 알바는 고용 중에만 보인다. 캠프는 역할별 색의 별명과 대사 또는 작업 상태를 한 줄로 묶어 캐릭터 머리 위 가로 중심에 맞춘다. 대기 중인 캐릭터는 캠프 안을 이동하거나 가까운 동료와 잡담한다.
- R12: 업무 로그에 역할·모델별 실행 횟수와 시간을 표시하고, 확인 가능한 사용량과 비용을 남긴다. 모델 실행 환경이 사용 한도 도달을 알리면 해당 업무를 멈추고 비서가 진행한 부분과 남은 일을 알린다.
- R14: 비서를 통해 앱 도우미에게 사용법과 앱 조작을 요청할 수 있다. 사용자가 화면에서 실행할 수 있는 모든 동작은 자체 MCP에도 등록되고 같은 권한·승인·저장·이력 규칙을 사용한다. 조작 결과는 실제 대상 화면에 반영되며 비서는 원래 채팅에서 결과를 알린다.
- R15: 사용자와 비서의 대화는 좌우 말풍선으로 구분한다. 전송 후 응답 또는 선택한 업무의 멈춤으로 전환하고, 그동안 추가 지시를 보낼 수 있다. 좁은 창·키보드에서도 같은 대상에 같은 동작이 적용된다.

- R16: 목업의 입력창은 첫 전송 전후 같은 위치에 있고 네 탭은 같은 패널을 쓴다. 승인 전에는 질문이 입력창 위에 한 번, 승인 후에는 결정이 로그에 한 번 남는다. 캠프·카드·로그는 같은 업무의 상태를 읽으며 이전 세션 초안과 진행은 세션을 바꿔도 이어진다.

## Design

- 데스크톱 화면은 Electron Forge의 **Vite + TypeScript 템플릿**에 React를 붙인다. 폴더 선택은 Electron `dialog`, 화면과 메인 프로세스 연결은 `contextBridge`·`ipcMain`·`ipcRenderer`를 사용한다. 탭·모델 선택·확인 창은 Radix Primitives의 `Tabs`·`Select`·`Dialog`를 쓰고, 업무 카드와 로그는 React로 구성한다. IPC, 도구 인자, 에이전트가 반환한 구조화 결과처럼 경계를 넘는 입력은 **Zod**로 검증한다. (R1, R2, R4, R5, R6, R8, R10, R12) [Forge 템플릿](https://www.electronforge.io/templates/vite-%2B-typescript), [Electron 컨텍스트 격리](https://www.electronjs.org/docs/latest/tutorial/context-isolation), [Radix Primitives](https://www.radix-ui.com/primitives/docs/overview/introduction), [Zod](https://zod.dev/)
- 로컬 저장은 Electron 메인 프로세스의 **`node:sqlite`**로 처리한다. SQL 마이그레이션, 준비된 문장과 트랜잭션으로 프로젝트별 채팅과 세션 설정, 모델 세션 참조, 업무 상태와 로그, 워크플로우 버전, 에이전트별 메모리, 공유 위키 본문과 변경 이력을 저장한다. 위키 편집은 문서 갱신과 변경 이력을 같은 트랜잭션으로 기록한다. `/clear`는 새 세션을 만들고 이전 이력을 유지한다. 업무 상태 변경과 그에 대응하는 로그는 같이 기록한다. (R1, R2, R3, R5, R6, R7, R8, R9, R10, R12) [Node.js SQLite](https://nodejs.org/api/sqlite.html)
- **Codex App Server**는 `node:child_process.spawn`으로 시작하고, `node:readline`으로 표준 입출력의 JSONL을 읽는다. 설치된 App Server가 생성하는 TypeScript 스키마를 프로토콜 타입으로 사용한다. 기존 API로 세션 재개와 실행 중 추가 지시·중단을 처리한다. (R2, R4, R5, R8, R12) [Codex App Server](https://developers.openai.com/codex/app-server), [Node.js 프로세스](https://nodejs.org/api/child_process.html), [Node.js readline](https://nodejs.org/api/readline.html)
- 로컬 모델은 보유 환경이 OpenAI 호환 엔드포인트를 제공하면 **AI SDK**(`ai`, `@ai-sdk/openai-compatible`)로 스트리밍과 도구 호출을 연결한다. 앱이 보관한 세션 맥락과 등록 도구를 넘기고, 지원되는 취소 경로에는 `AbortSignal`을 전달한다. MCP는 Codex의 기본 연동과 앱의 **공식 MCP TypeScript SDK** 클라이언트를 재사용한다. 로컬 모델이 요청한 테스트 등 프로젝트 명령은 권한 확인 뒤 App Server의 샌드박스 실행 API `command/exec`를 사용한다. 실제 환경에서 역할별 권한과 중단 동작을 검증한다. (R2, R4, R5, R8, R12) [AI SDK 호환 제공자](https://ai-sdk.dev/providers/openai-compatible-providers), [도구 호출](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling), [MCP SDK](https://github.com/modelcontextprotocol/typescript-sdk), [Codex App Server](https://developers.openai.com/codex/app-server)
- **디자인 토큰**은 작업 패널 크기, 간격, 컨트롤, 색, 노드 치수를 공통 CSS 변수로 정의한다. 대화·로그·메모리·워크플로우는 같은 레이아웃을 사용한다. (R10, R15) [화면과 동작 명세](../interaction.md)
- 입력창·업무 카드·캠프는 업무 및 응답 ID에 연결된 실행 상태를 읽는다. React가 관리하는 선택·초안·스크롤은 실행 상태와 구분한다. 화면 명세의 조작 표를 해당 구현 단계의 인수 기준으로 사용한다. (R5, R6, R11, R15) [화면과 동작 명세](../interaction.md)
- 자체 MCP는 공식 MCP TypeScript SDK로 앱의 조작 검색·상태 조회·동작 실행을 제공한다. Electron 메인 프로세스에서 화면 IPC와 MCP가 같은 사용자 동작 실행기를 호출하고 동일한 입력 검증, 권한과 상태 검사, 기록을 사용한다. 기능 범위와 결과 계약은 [앱 도우미와 AI Crew MCP](../app-mcp.md)를 따른다. (R4, R5, R6, R14)
- **XState**는 업무 상태 전이와 완료 조건을 표현하는 데 쓴다. 비서는 역할과 담당자를 선택하고, 업무 규칙이 필수 검증 통과·재시도 횟수·현재 권한을 판단한다. 지시와 검증 결과는 업무별로 저장하며, 같은 에이전트 세션이나 겹치는 작업은 순서대로 실행한다. 재시작 시 SQLite의 업무 상태를 읽어 표시하고 사용자 지시 후 실행을 재개한다. (R1, R2, R3, R4, R5, R6, R10, R12) [XState 상태 전이](https://stately.ai/docs/transitions), [XState 전이 조건](https://stately.ai/docs/guards)
- 변경 검증에는 **Git CLI**, `node:fs`·`node:crypto`, **jsdiff**(`diff`)를 사용한다. Git 프로젝트는 상태·diff 조회를 재사용한다. 업무 시작 전 기준과 완료 시점의 대상 파일 내용을 비교해 기존 변경과 업무 변경을 구분하고, 변경 버전에 검토·테스트를 연결한다. Git이 없는 폴더에서도 대상 텍스트 파일의 내용과 해시를 기준으로 검증하며, 텍스트 차이는 jsdiff로 계산한다. (R3, R5, R6) [Git diff](https://git-scm.com/docs/git-diff), [Node.js fs](https://nodejs.org/api/fs.html), [jsdiff](https://github.com/kpdecker/jsdiff)
- 인사팀: 비서가 요청한 역할과 기존 권한에 맞춰 에이전트를 준비한다. 비서의 채택·투입·해고 결정을 상태에 반영하고, 해고 후에도 설정과 이력을 보존한다. (R4, R7, R11)
- 캠프와 범례는 **Phaser**의 스프라이트·애니메이션·Tween을 쓴다. **Tiled**에서 이동 경로와 영역을 정리해 JSON으로 내보내고, **Aseprite**에서 캐릭터 스프라이트 시트를 만든다. 풍부한 캠프 배경과 가림 물체, 캐릭터, 불꽃·마법진을 레이어로 나눈다. 캐릭터 동작은 짧게 재사용하고, 대기 중 이동과 잡담은 경로와 대사로 연출한다. 실제 업무 상태가 우선이며, 장면에서 해당 업무 카드나 로그로 이동한다. (R6, R11) [Phaser 애니메이션](https://docs.phaser.io/phaser/concepts/animations), [Phaser 타일맵](https://docs.phaser.io/api-documentation/class/tilemaps-tilemap), [Tiled](https://doc.mapeditor.org/en/stable/), [Aseprite 스프라이트 시트](https://aseprite.org/docs/sprite-sheet/)
- 검증은 **Vitest**로 업무 전이·권한·SQLite 복구를 확인하고, **Playwright의 Electron 지원**으로 폴더 선택 후 채팅·카드·로그가 이어지는 화면을 확인한다. 실제 Codex와 로컬 모델을 함께 쓰는 업무는 별도 통합 시나리오에서 실행한다. (R1, R2, R3, R4, R5, R6, R8) [Vitest](https://vitest.dev/guide/), [Playwright Electron](https://playwright.dev/docs/api/class-electron)

- 목업의 업무 이벤트는 `demo/model.js`가 만들고, `demo/camp.js`는 같은 이벤트에서 대화·로그·캠프와 메뉴를 갱신한다. `demo/index.html`과 `demo/camp.css`는 작업 패널을 고정하고 `demo/tokens.css`를 네 탭이 공유한다. 캠프 그림과 React Flow는 기존 자산·연결 동작을 재사용한다. `demo/workflow.js`는 연결을 실행 그룹으로 변환하고, `demo/flow/editor.jsx`와 `editor.css`는 편집과 저장 상태를 표시한다. (R6, R11, R15, R16)

## Decisions

- T8에서 핵심 업무 흐름을 확인한다. T9부터는 완성본의 세션·메모리·모델 한도 처리와 캠프 동작을 구현한다. [제품 구상](../concept.md)
- 첫 설치 때 Electron과 Forge·Vite의 호환 버전을 고정하고 잠금 파일을 커밋한다. Forge의 Vite 플러그인과 Playwright의 Electron 지원은 공식 문서상 실험 기능이므로, 선택한 버전으로 패키징과 앱 시작을 확인한다. SQLite는 설치된 Electron의 내장 Node에서 작동하는지 먼저 확인한다. [Forge Vite](https://www.electronforge.io/config/plugins/vite), [Playwright Electron](https://playwright.dev/docs/api/class-electron)

- Aseprite는 공개 소스를 제작자의 로컬 환경에서 직접 빌드해 사용한다. AI Crew 패키지에는 제작한 스프라이트와 애니메이션 데이터만 넣는다. [Aseprite 빌드 안내](https://github.com/aseprite/aseprite/blob/main/INSTALL.md), [Aseprite FAQ](https://aseprite.org/faq)
- 첫 워크플로우는 한 프로젝트에서 쓰기 작업 한 건으로 검증한다. 기본 개발 흐름은 플랜 인계 후 개발에 착수한다. 별도의 플랜 리뷰가 필요한 프로젝트는 편집기에서 추가한다. 세 검증 담당자는 같은 변경 버전을 독립적으로 확인한다.
- 프로젝트 결정과 근거는 공유 위키에 기록하고, 실행에 적용할 단계와 완료 조건은 업무에 연결된 워크플로우 버전에서 읽는다. 이전 작업을 이어갈 때는 해당 세션을 로드한다. 실행 환경 때문에 기존 에이전트 세션을 이어갈 수 없으면 새 실행으로 마지막 결정·변경·남은 일을 넘긴다.
- 재실행 전에 앞선 작업의 반영 여부를 확인한다. 변경 전 지시나 파일 버전에 대한 늦은 검증 결과는 해당 업무의 이력에 남기고, 완료는 최신 지시와 변경에 대한 검증으로 판단한다.

- [ ] T3. 플랜 인계와 개발 위임 연결 (R2, R3, R4, R6)
  - Done when: 플랜 담당이 요구사항별 작업 범위와 확인 가능한 완료 조건을 남기면 비서가 개발 담당에게 위임해 실제 파일을 바꾼다. 같은 역할 후보가 여럿이면 비서가 담당자를 고른다. 각 담당자는 자기 세션에서 작업한다. 읽기 권한으로 파일을 수정하려 하면 차단된다.
  - **동료끼리 직접 요청.** 개발 담당이 같은 업무 안에서 스타일 담당에게 대상 파일과 질문을 보내면 스타일 담당이 개발 담당에게 직접 답한다. 요청 ID에 업무·단계, 보낸 사람, 받을 역할, 기대 결과와 응답을 묶는다. 받을 사람이 여럿이면 비서가 고르고, 바쁘면 대기열에 둔다. 요청자의 권한은 전달되지 않는다. 필수 단계가 아닌 조언은 다른 작업과 병행할 수 있다.
  - **확인 사례.** 개발 담당이 스타일 검토를 기다릴 때 스타일 담당이 원래 요청의 추가 설명을 요구해도 양쪽이 영구 대기하지 않아야 한다. 보완은 기존 요청에 이어 붙이고, 같은 요청 ID를 다시 받아도 실행은 한 번이다. 새 대기 관계를 추가할 때 순환을 검사한다. 독립적인 새 요청이 순환을 만들면 대기 관계 등록을 보류하고 비서가 담당이나 순서를 조정한다. 로그에는 왕복이 보이고 사용자 채팅에는 권한·범위 등 판단이 필요한 경우에만 비서의 질문이 뜬다.
  - **인계 내용.** 보내는 쪽은 목적·완료 조건, 담당자, 지시 버전, 대상 변경 버전, 산출물 위치, 확인한 근거, 남은 일과 다음 담당자가 할 일을 기록한다. 전략 인계는 아직 파일 변경이 없어도 작업 계획과 완료 조건으로 성립한다. 개발 인계에는 변경 파일과 기준 버전, 테스트 인계에는 실행 명령·결과·미검증 항목을 담는다. 받는 쪽이 필수 산출물을 찾지 못하면 같은 인계에 보완을 요청한다.
  - **인계 검증.** 개발 인계 뒤 파일이 다시 바뀐 상태에서 예전 버전의 리뷰가 도착하면 기록은 열 수 있고 최신 버전의 완료 조건은 미충족으로 남는다.
- [ ] T4. 리뷰·코딩 스타일 확인·테스트, 최종 보고와 후속 수정 연결 (R3, R4, R6)
  - Done when: 리뷰·스타일·테스트 담당이 같은 변경을 확인하고 세 결과를 남긴다. 업무 전에 이미 있던 변경을 이번 변경과 구분하고, Git이 없는 테스트 폴더에서도 변경을 확인할 수 있다. 최신 변경의 필수 확인이 통과하면 비서가 변경 파일과 검증 결과를 보고한다. 완료한 결과의 수정을 요청하면 같은 업무의 카드가 다시 나타나고 기존 보고와 새 검증이 함께 남는다.
  - **겹치는 수정 범위.** 쓰기 전 메인 프로세스가 프로젝트의 실제 경로 기준으로 파일·디렉터리 범위를 예약한다. 한 단계에 필요한 범위를 함께 확보하고, 같은 파일·상하위 경로·이동 전후 경로가 겹치면 뒤 작업을 대기시킨다. 명령의 쓰기 범위를 제한할 수 없으면 프로젝트 전체를 예약한다. 작업 중 범위가 넓어지면 새 쓰기 전에 기존 변경을 기록하고 범위를 다시 확보한다.
  - **충돌 검증.** 서로 다른 세션에서 같은 파일을 수정하면 두 번째 담당자가 첫 변경을 읽은 뒤 시작한다. 범위와 의존성이 다른 두 파일은 동시에 진행할 수 있다. 대기 중 사용자가 직접 고친 파일도 쓰기 직전 기준과 비교해 재검토한다. 취소·종료 때 실제 쓰기가 끝났음을 확인한 뒤 예약을 해제한다. 재시작 뒤 실행 여부가 불분명하면 먼저 확인한다.
- [ ] T5. 추가 지시·재시도·중단 및 세션 재개 연결 (R1, R2, R4, R5, R6, R15)
  - Done when: 일시적 실패와 수정·재검증은 각각 최대 3회 반복하고 해결되지 않으면 비서가 막힌 이유를 보고한다. 추가 지시는 해당 업무에만 반영하고 이전 검증은 이력에 남긴다. 같은 에이전트 세션의 업무는 순서대로 실행하고 독립적인 다른 업무는 계속한다. 중단 요청 시 `중단 중`, 실제 정지 후 `중단됨`을 표시하며 기존 변경을 보존한다. 앱 종료 뒤 세션을 로드하면 사용자 지시 후 재개하고, 회수된 권한의 재요청은 현재 승인 정책으로 처리한다.
  - **세션을 이어갈 수 없을 때.** 실행 연결이 잠시 끊기면 기존 실행과 마지막 완료 단계를 먼저 조회한다. 모델 변경·세션 만료·재개 미지원으로 복원이 불가능하면 같은 앱 업무 아래 새 모델 실행을 연결한다. 현재 권한으로 읽을 수 있는 마지막 결정·변경·검증 근거·남은 일과 인계 링크를 넘기고 전환 이유와 이전 실행 참조를 로그에 남긴다. 모델이 한도 도달을 알렸을 때는 해당 업무를 정지한다.
  - **중단·완료 검증.** 같은 업무의 완료와 중단을 순서를 바꿔 접수한다. 완료 확정이 먼저면 완료 보고만 남긴다. 중단 접수가 먼저면 후속 배정은 닫히고 뒤늦은 결과는 이력에만 남는다. 상태 전이와 대응 로그는 한 트랜잭션으로 기록한다. 정지를 확인할 때까지 수정 범위 예약을 유지한다.
  - **복구 검증.** 파일 저장 직후 모델 세션이 사라져도 실제 파일과 실행 기록으로 저장 여부를 확인하고 남은 검토부터 진행한다. 외부 변경 여부가 불명확하면 기존 호출의 결과를 조회하고, 확인할 수 없으면 사용자 답변을 기다린다. 답변 전에는 동일한 외부 동작의 재시도 횟수가 0회여야 한다. 사용자 세션과 업무 카드는 하나로 유지된다.
  - **모호한 추가 지시.** 업무가 두 건 진행 중일 때 “그거 다시 해줘”라고 하면 비서가 후보 업무명을 질문 아래 카드에 표시한다. 답이 올 때까지 새 지시를 보류하고 기존 업무는 원래 지시대로 진행한다. 업무가 명확해도 바꿀 내용이 모호하면 해당 부분을 물어본다. 사용자가 선택하면 업무 ID와 지시 버전을 기록하고 영향받는 단계만 재검증한다.
  - **확인 사례.** 답변 전에 선택한 업무가 끝났다면 그 결과에 대한 수정으로 같은 업무를 재개한다. 다른 업무의 지시·검증 버전은 그대로여야 한다.
- [ ] T6. 인사팀 고용과 비서의 채택·해고 연결 (R4, R6, R7)
  - Done when: 기존 팀에 없는 역할을 요청하면 인사팀이 에이전트를 고용하고 비서가 채택한 뒤 업무에 투입한다. 정규 팀원은 이후 업무에서도 선택 가능하다. 알바는 목표를 달성하면 비서 판단으로 퇴장하고 결과와 업무 기록은 남는다.
  - **해고 동작.** 범례 조작과 비서 결정은 같은 고용 상태를 갱신한다. 즉시 새 배정을 닫고, 아직 시작하지 않은 요청은 비서가 다른 담당자에게 돌린다. 진행 중이면 범례에 ‘퇴장 예정’을 표시하고 맡은 단계의 결과 또는 중단 인계를 저장한 뒤 퇴장한다. 확인할 것은 해고를 두 번 눌러도 인계·퇴장이 각각 한 번이고, 정규 팀원은 미고용 상태에서 기존 설정으로 재고용된다는 점이다.
  - **퇴장한 알바의 일.** 원래 업무에 알바의 작성자 ID·당시 역할, 산출물·변경 버전, 검증 결과와 미결 요청을 보존한다. 퇴장 후 수정 지시나 늦은 리뷰가 들어오면 비서가 같은 업무에 연결한다. 남은 일을 맡을 팀원이 없으면 인사팀이 후보를 준비하고 비서가 채택한다. 새 담당자는 저장한 인계와 본인의 권한으로 이어간다.
  - **확인 사례.** 알바 해고 후 범례에서 사라진 상태로 기존 결과의 수정을 요청한다. 같은 업무에서 이전 산출물과 새 담당자의 변경을 모두 열 수 있고 퇴장한 알바에게 새 요청이 전달되지 않아야 한다.
- [ ] T7. 고정 업무 카드·답변 카드·상세 로그 연결 (R4, R5, R6, R7, R15)
  - Done when: 한 세션에 업무별 카드가 고정된다. 수동 모드의 새 접근 권한 요청은 입력창 바로 위에 한 번 나타난다. 승인 카드의 업무명으로 상세를 열고 답변은 해당 업무에만 적용된다. 완료한 업무는 상단에서 빠지고 비서 보고는 남는다. 업무 로그에서 시각·역할·행동·결과와 함께 변경 파일, 검토 의견, 테스트 명령과 결과, 실패 원인을 확인할 수 있다.
  - **작업 공간 선택과 승인.** 좁은 창에서도 보내기 줄에 현재 폴더와 승인 모드가 보인다. 세션은 탭 오른쪽 ☰ 아래 목록에서 고른다. 제목은 목록에서 읽고, 바깥을 누르거나 Esc를 누르면 목록이 닫힌다. 같은 창 크기에서 네 탭의 작업 패널 폭과 높이가 일치하며 워크플로우 초안은 탭을 오가도 유지된다. 세션을 선택하면 해당 초안과 업무를 복원한다. 동일한 권한 요청을 세 모드에서 실행해 결정 주체와 적용 시점, 거절 후 후속 작업 중단, 프로젝트별 격리를 확인한다.
  - **요청부터 결과까지.** 상태 질문과 위키 요약은 현재 데이터를 조회한다. 별도 요청과 특정 업무의 추가 지시를 구별한다. 승인 전후의 담당자 상태를 캠프에서 확인하고 완료 보고에서 같은 업무의 검증 로그를 한 번에 연다.
  - **대화 조작 검증.** 입력 조합 중 Enter, 전송 직후 연속 클릭, 업무 두 건 중 한 건 멈춤, 응답만 중단, 초안이 있는 상태에서 추가 지시, 권한 질문 중 세션 전환을 재현한다. 말풍선의 개수와 업무별 로그를 대조하고 좁은 창·키보드에서 같은 동작을 확인한다.
  - **스킬과 MCP 관리.** 범례에서 담당자를 선택하면 정의 MD, 배정된 스킬, 연결된 MCP 서버와 허용 도구·접근 범위를 확인한다. 사용자는 해당 역할의 스킬을 추가·해제하고 서버·도구 권한을 부여·회수할 수 있다. 스킬에 도구 호출 지침이 있어도 실행기는 호출 시점에 그 담당자의 현재 허용 목록을 검사한다. 연결 불가와 권한 부족은 로그에서 구분해 비서가 재연결 또는 승인 중 필요한 조치를 안내한다.
  - **권한 검증.** 같은 서버에서 개발 담당에게 쓰기 도구, 리뷰 담당에게 읽기 도구만 허용한다. 개발 담당의 쓰기 권한을 대기 중에 회수하면 이미 대기하던 호출과 이전 세션에서의 다음 호출도 차단된다. `src/search.ts` 수정 승인 뒤 다른 파일을 추가하면 새 요청 ID로 범위를 표시하고, 옛 질문에 대한 클릭으로 새 호출이 실행되지 않아야 한다. `항상` 모드에서도 읽기만 허용된 리뷰 담당의 쓰기 호출은 차단된다. 권한 변경은 사용자·대상·변경 내용과 함께 기록하고 인증값은 로그에 남기지 않는다.

  - Done when: `빈 검색어는 전체 목록을 보여주게 바꿔줘`를 비서에게 요청하면 사용자가 연 테스트 프로젝트의 파일이 직접 바뀐다. 플랜 인계와 세 갈래 검증 결과를 확인하고, 같은 업무에서 Codex와 로컬 LLM이 맡은 결과가 로그와 최종 보고에 남는다. 테스트 실패 시 `수정 중`으로 바뀌고 최신 수정분을 재검증한다. 전문 역할의 고용 기록을 확인한다. 앱 종료 후 이전 세션을 로드하고 사용자 지시로 남은 업무를 이어간다.
- [ ] T9. 이전 설정 로드와 채팅 슬래시 명령 연결 (R1, R2, R9)

  - **입력 검증.** 입력창에 `/`를 치면 등록된 명령과 설명을 표시한다. 명령 목록과 전송 처리는 같은 등록 정보를 사용한다. `/clear`만 전송하면 앱이 모델 호출 없이 새 세션으로 전환한다. “/clear가 뭐야?”를 전송하면 기존 세션에서 비서가 질문에 답한다.
- [ ] T10. 프로젝트 워크플로우와 메모리 탭 연결 (R9, R10)
  - Done when: 새 규칙은 다음 새 업무에 적용되고, 진행 중인 업무는 사용자가 지정했을 때 적용된다. 이전 세션을 로드해 새 업무를 만들어도 현재 규칙을 적용한다. 비서가 남긴 메모리는 탭에서 출처와 시각을 확인하고, 규칙이 연결된 항목은 기억만 지우거나 규칙도 함께 해제할 수 있다.
  - **앱 내 React Flow 편집기.** 워크플로우 탭에서 요청부터 보고까지 위에서 아래로 배치한다. 병렬 단계는 같은 높이에 두고, 각 노드 아래 연결점에서 다음 노드 위 연결점으로 마우스를 끌어 잇는다. 노드를 두 번 누르면 속성을 편집한다. React 화면에 MIT 라이선스의 `@xyflow/react`를 사용한다. 단계 노드에는 캠프 범례와 같은 역할명·색을 쓰고, 저장하면 같은 탭에 적용 버전을 표시한다. 대화 탭으로 돌아오면 원래 세션과 선택한 업무 카드가 유지된다. 편집 화면을 열거나 닫아도 진행 중인 업무는 계속된다.
  - **편집과 실행 연결.** 노드의 단계 ID와 연결선으로 실행 순서·분기·병렬 합류를 정의한다. 캔버스 좌표는 화면 배치에만 사용한다. Electron 메인 프로세스가 프로젝트 규칙을 검증한 뒤 SQLite에 버전과 배치를 저장한다. 실행은 기존 업무 엔진(XState)이 담당한다. 편집기에 다시 열었을 때 연결과 배치가 유지되고, 비서와 편집기가 동시에 규칙을 바꾸면 이전 버전의 저장이 최신 변경을 덮어쓰지 않도록 한다.
  - **편집기 검증.** 패키징한 Electron에서 워크플로우 탭의 React Flow 편집기를 열고 노드를 드래그한 뒤 연결점을 마우스로 이어 개발 뒤 리뷰·코딩 스타일 확인·테스트를 병렬로 연결하고 저장한다. 새 업무에서 세 결과가 모두 같은 변경 버전을 통과해야 비서에게 결과가 전달되는지 확인한다. 편집기를 다시 열면 역할과 연결선이 복원되고, 노드 위치만 옮겨도 실행 순서는 유지돼야 한다. [React Flow 공식 문서](https://reactflow.dev/learn)
  - **워크플로우 편집.** 프로젝트에서 업무 종류를 고르고 단계 추가·삭제와 인계 산출물·완료 조건을 편집한다. 순서와 병렬 실행은 그래프 연결점으로 지정한다. 저장 전에 끊긴 참조, 순환 의존, 완료까지 도달할 수 없는 단계를 검사한다. 실행 조건이 맞지 않아 건너뛴 단계는 합류에서 대기 대상으로 세지 않는다. 적용 대상인 필수 단계가 실패하면 완료 경로를 닫고 정해 둔 한도 안에서 수정·재검증으로 이어간다. 비서에게 말로 바꾼 규칙과 편집 화면에서 저장한 규칙은 같은 프로젝트 버전을 사용한다.
  - **적용 검증.** 접근성 검토를 추가하면 다음 새 업무에는 필수로 뜨고 진행 중 업무는 시작 당시 버전을 유지한다. “이번 업무에도”를 지정하면 해당 업무의 남은 단계와 재검증 대상을 다시 계산한다. “이번에만”으로 추가한 단계는 다음 업무에 나타나지 않는다. 잘못된 편집을 저장해도 마지막 유효 버전이 유지된다. 조건부 단계가 건너뛰어져도 남은 필수 단계가 최신 결과를 검증하면 완료된다. 같은 그래프에서 필수 테스트를 실패시키면 수정·재검증이 끝날 때까지 완료 보고가 없어야 한다.
  - **에이전트별 메모리.** 기억마다 프로젝트, 소유 범위(프로젝트 공통 또는 에이전트 ID), 작성자, 출처 업무·세션, 기록 시각을 저장한다. 담당자는 다음 작업에 쓸 기억을 스스로 남길 수 있다. 다음 실행에는 본인 기억과 현재 프로젝트 위키 목차를 제공하고 업무에 관련된 문서를 읽게 한다. 업무 결과를 다른 담당자에게 전달할 때는 인계를 사용한다. 별명을 바꿔도 기억의 소유자는 유지된다.
  - **위키 노드 보기.** 목차와 그래프는 같은 프로젝트 문서 ID를 사용한다. 문서 간 명시적 참조를 방향 있는 연결선으로 표시하고, 고립 문서도 선택해 본문·출처를 연다. 제목 변경 시 동일 ID를 유지하고 삭제된 문서와 연결선은 그래프에서 제거한다.
  - **메모리 탐색.** 메모리 탭에서 프로젝트 위키와 에이전트 기억을 전환한다. 목록·노드 전환은 위키 안에 두고, 담당자 상세에서 해당 기억을 바로 연다.
  - **프로젝트 위키 화면.** 메모리 탭의 주제별 목차에서 최신 본문을 읽고 편집·삭제한다. 변경 타임라인은 문서 생성과 수정을 구분하며 시각, 작성자, 제목을 표시한다. 변경을 선택하면 당시 추가·수정한 문장과 출처 업무나 파일을 연다. 워크플로우 결정에 관한 문서는 적용 중인 규칙과 연결한다.
  - **축적 과정 검증.** 테스트 담당이 ‘테스트 방법’을 만들고 개발 담당이 다음 업무에서 실행 명령을 보완한다. 목차에는 문서 한 건, 타임라인에는 서로 다른 작성자의 변경 두 건이 보여야 한다. 두 번째 변경에서 추가된 명령과 출처 업무를 열고, 앱을 완전히 종료했다가 같은 프로젝트의 새 세션을 열어도 보완된 본문과 두 변경 기록을 읽을 수 있어야 한다.
  - **메모리 검증.** 대화·로그 옆 메모리 탭에서 공통 기억과 담당자별 기억을 보고 삭제한다. 범례에서 담당자의 메모리를 누르면 같은 탭에 해당 필터가 열린다. 삭제한 기억은 이후 실행의 메모리 입력에서 빠지고 원래 대화와 업무 로그는 남는다. 다른 프로젝트의 같은 역할에게 노출되지 않아야 한다.

- [ ] T12. 캠프 시각화와 범례의 고용 상태 연결 (R6, R7, R11, R15)
  - Done when: 위임·작업은 캠프에 표시되고 장면에서 해당 업무를 열 수 있다. 대기 캐릭터가 지정 경로를 스스로 이동하고 짧은 대사가 역할별 색의 별명 옆에 뜬다. 대사 유무나 길이가 바뀌어도 줄 전체의 가로 중심이 캐릭터 중심에 맞는다. 범례에는 에이전트만 나오고, 역할 옆의 별명 텍스트를 눌러 수정하면 캐릭터 위 표시도 바뀐다. 정규 팀원은 해고 후 목록에 남아 기존 설정으로 재고용할 수 있고, 알바는 고용 때 목록에 추가되고 해고 때 목록에서 빠진다. 고용과 해고에 맞춰 캐릭터가 화면 밖에서 들어오거나 나간다.
  - **채팅과 캠프 연결.** 업무 상태를 저장한 이벤트에 프로젝트·세션·업무 ID, 담당자, 요청·인계 ID를 연결한다. 카드·로그·캠프는 같은 기록을 읽는다. 채팅 카드에서 업무를 선택하면 캠프에서 참여자를 강조하고, 캠프에서 인계 장면을 선택하면 해당 요청의 로그를 연다. 캐릭터에 업무가 여러 건 연결되면 업무명을 골라 연다. 완료해 카드가 사라진 업무는 로그와 비서 보고로 연결한다.
  - **연결 검증.** 한 세션에서 두 업무를 병행하고 다른 세션을 다녀와도 선택한 업무만 강조된다. 캠프를 늦게 열면 저장된 현재 상태를 표시하며 과거의 고용이나 위임을 다시 실행하지 않는다. 대기 잡담은 실제 요청이나 채팅 메시지를 만들지 않는다.
